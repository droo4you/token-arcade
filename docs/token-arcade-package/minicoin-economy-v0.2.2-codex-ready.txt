2. What Token Arcade is
Token Arcade is a browser arcade for onchain communities, with Metropolis v0
launching on Monad.
A Cabinet can exist without a MiniCoin. A MiniCoin can be a standalone game
economy, or it can be connected to an existing Community Asset through one
or more configurable Strategies.
The MiniCoin itself is not the Strategy.
End-to-end value logic:

Economy Router allocates captured value

Principles:
• No inflationary gameplay emissions. MiniCoins are never minted as
rewards. Rewards come only from assets already collected, acquired, or
deposited.
• No player-funded wagering in v0. Metropolis Raids are free-entry
and rewards are pre-funded. Paid Ranked entry remains later/legal-review
scope.
• No floor sweeping in the swap path. v0 does not buy Community
Assets during a swap.
• No implied fund ownership. MiniCoin holders do not automatically
own or redeem Strategy/Vault/Treasury assets.
• Game first, economy optional. A Cabinet can launch now and add
an approved MiniCoin later without changing its gameId or resetting its
leaderboard history.

5. The MiniCoin token
• Plain ERC-20.
• Fixed supply, minted once at launch to the Factory/launch flow.
• No mint function after deployment.
• No transfer tax.
• No blacklist.
• No owner-only pause.
• The token itself does not implement game rewards or Community Asset
logic.
Why no transfer tax: v4 pool settlement expects exact token movement; fee-on-
transfer behavior complicates/desynchronizes pool accounting. The economic
fee belongs at the hook/pool layer, not inside the ERC-20.
Supply (proposal): 1,000,000,000 tokens, 18 decimals.
Allocation (proposal): founder-deployed v0 default is 0% creator allocation
and the remaining launch supply used for initial liquidity. Future creator allo-
cation may be capped at 5% and vested, but exact creator economics are not
frozen for Metropolis.
Token Arcade does not require a $TA allocation. Protocol funding comes from
the configured Treasury share.
6. Pool and pair asset
v0 pair asset: WMON only .
WMON = 0x3bd359C1119dA7Da1D913D1C4D2B7c461115433A
Direct MiniCoin/Community Asset pairs are an architectural possibility for
later. They are not required for Metropolis.
PoolKey v0 (proposal):
• currencies: MiniCoin + WMON, sorted by address
• LP fee: 3000 = 0.30% static
• tick spacing: 60
• hook: current approved MiniCoinHook version
• dynamic-fee flag: not used in v0
The v4 LP fee and Token Arcade’s custom hook fee are separate mechanisms.
A pool’s hook is part of its PoolKey and cannot be replaced. A bad hook requires
a new approved hook version, new pool, and controlled liquidity migration.

7. MiniCoinHook v1 - tiny, swap-critical
The hook should remain deliberately small.
Frozen economic responsibilities
1. Gate/validate approved pool initialization as required by the chosen Fac-
tory/deployment path.
2. Charge the configured custom hook fee on the WMON leg of a swap.
3. Attribute the captured WMON fee to the correct PoolId so it can later
be distributed by EconomyManager.
v0 hook fee (proposal): 100 bps = 1.00% of the WMON leg.
Hard ceiling: 500 bps = 5.00% .
Per-pool hook fee is immutable for that pool in v0.
Swap-path rules
• only the PoolManager may invoke callbacks
• no Raid logic on the swap path
• no Community Asset purchase on the swap path
• no reads of Raid/Vault/Strategy state to decide whether swaps succeed
• no mutable admin function that changes an existing pool’s hook behavior
• external failure in a downstream Strategy/Raid component must not brick
the pool
Implementation hypothesis warning
The exact Uniswap v4 custom-accounting / PoolManager settlement calls used
to capture/attribute WMON are an implementation hypothesis, not a
frozen Solidity API .
Codex must validate the current installed Uniswap v4 interfaces and Monad
deployment before implementing. Preserve the economic invariant - WMON
hook fee is attributable by PoolId and later distributable - but refactor cus-
tody/accounting details if required to keep failure out of the swap-critical path.
Versioning
Each approved MiniCoinHook version may serve many pools. The Fac-
tory/Registry points new launches to the current approved version. Existing
pools do not mutate to a new hook.

9. PrizeVault
• One PrizeVault per MiniCoin, preferably minimal clone/proxy pattern if
appropriate after security review.
• Holds WMON from RaidFundingStrategy.
• Can also hold manually deposited approved ERC-20 and ERC-721 re-
wards.
• Tracks free vs Raid-locked balances.
• Pays only what it holds; never mints.
• No arbitrary admin withdraw(address).
• Funds leave through approved Raid escrow/claim/cancel/migration paths
only.
When an Economy Raid opens, PrizeVault reserves the Raid’s prize from free
balance.

10. Triggers, Raids, verification, settlement,
claims
v0 trigger: VaultThreshold only
openEconomyRaid(gameId) can succeed when:
• the MiniCoin PrizeVault free balance >= configured threshold
• no conflicting Economy Raid is active for that Cabinet
• configured cooldown has passed
• the Cabinet/Verifier/economy configuration is still valid
When it opens:
• WMON prize is reserved from the Vault
• optional pre-approved/manual NFT hero reward may also be queued
• Raid start/end/rules are recorded
• RaidOpened(...) is emitted
Why VaultThreshold only in v0:
• objective and onchain
• cheap to evaluate
• forcing the trigger by trading also pays the fees funding the Raid
• volume triggers invite wash-trading design problems
• market-cap triggers need oracle/TW AP design
• holder count/concurrent-player triggers need offchain/indexed inputs
Funded Raids
A Cabinet does not need a MiniCoin to run a Funded Raid. An opera-
tor/community/sponsor may deposit approved rewards and create a Raid
through the same settlement layer.
Score Verifier
The browser is never the final authority.
Each Cabinet declares one verifier approach:
• session/telemetry validation - authenticated run token plus game-
specific checks/plausibility/telemetry

v0 settlement authorization
The v0 settlement signer is centralized and bounded to the escrow of the specific
Raid being settled.
For a Raid with WMON plus an optional hero NFT, use explicit reward seman-
tics rather than overloading one generic amount field.
A practical v0 settlement shape may be conceptually:

The Raid record already knows the escrowed ERC-20 asset/amount and optional
NFT contract/tokenId.
Players claim ERC-20 distributions with proofs to their Passport embedded wal-
let. The optional hero NFT is transferred only to the recorded winner through
the Raid settlement/claim path.
No settlement may distribute more than the Raid’s escrow.
Unawarded/unclaimed assets return to the appropriate source after configured
windows. If settlement never arrives, a timeout/cancel path returns escrow to
source.
Proposal: claim window 14 days; settlement timeout 7 days.

11. Launch structure - MiniCoinFactory
The product presents a single user-facing launch flow; atomic where
practical. Do not assume every step fits safely in one transaction until de-
ploy/approval/liquidity mechanics are tested.
Conceptual steps:
1. Deploy fixed-supply MiniCoin.
2. Initialize approved v4 MiniCoin/WMON pool with the current approved
Hook version.
3. Seed liquidity through PositionManager using an explicitly validated
launch config.
4. Lock/custody the LP position according to the approved migration policy.
5. Create/wire PrizeVault, CommunityStrategy, EconomyManager/Raid
config.
6. Register gameId -> {MiniCoin, poolId, hookVersion, vault,
communityStrategy, communityAsset} .
7. Existing Cabinet flips from game-only to MiniCoin-enabled without chang-
ing gameId or leaderboard history.
Creator/Admin product lifecycle vs protocol authority
Product v0 uses:
SUBMIT -> ADMIN APPROVE -> DEVELOPER DEPLOY -> PUBLISHED
The developer initiates Deploy after approval .
This does not require giving every creator unrestricted Factory authority
in Metropolis v0. The approved Deploy action may invoke a platform-
controlled/allowlisted Factory path, Registry approval, signed launch autho-
rization, or equivalent constrained mechanism.
For the demo, the founder may act as both creator and admin.
Future v1 expands approved creator launch authorization after audit.
Future permissionless deployment must remain constrained to audited
templates/Strategies/guardrails.

17. Risks and guardrails
Hook / pool risk
• Keep Hook tiny.
• Treat current v4 call details as implementation hypotheses until com-
piled/tested against current dependencies.
• Fuzz conservation: captured fee == attributed/distributable fee.
• Do not let Raid/Strategy failure become swap failure.
• Hook cannot be patched in place; recovery means new Hook version/pool
+ controlled migration.
Vault / Raid risk
• no arbitrary admin withdrawal
• signer bounded to Raid escrow
• mixed ERC-20/ERC-721 settlement explicit
• cancellation/timeout returns assets to source
• hostile tests before creator launch expansion
Score cheating
• client untrusted
• game-specific Score Verifier
• session/rules/version binding
• replay protection
• deterministic replay only where practical, not a blanket rewrite require-
ment
