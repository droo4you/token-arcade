2. CONFLICT RULE
The two Sources of Truth govern different layers.
If implementation reveals a contradiction:
1. Stop the conflicting work.
2. Quote the exact conflicting requirements.
3. Identify which layer owns each requirement.
4. Do not invent a bridge or new product decision.
5. Ask for founder resolution.
6. Update the owning Source of Truth before continuing.
Examples:
• Can a game exist without a MiniCoin? Product Handoff owns the
UX; Economy Spec owns the economic implications. Both say yes.
• Does reusing a Skeleton reuse the leaderboard? Product Handoff:
no. Leaderboards belong to Cabinet deployments.
• How does a MiniCoin fee reach a Prize V ault? Economy Spec.

3. CURRENT PRODUCT IDENTITY RULES
These are already reflected in the Product Source of Truth and are repeated
here only as navigation aids:
• Gameplay Skeleton = reusable mechanics/rules.
• Cabinet / Deployment = the public game instance in Token Arcade.
• Separate Cabinets made from the same Skeleton get separate gameIds,
leaderboards, Raid histories, community associations, and optional
economies.
• The Player Passport may aggregate a player’s history across Cabinets.
• A reskin may create a new public Cabinet identity while preserving the
scored gameplay path.
• If scored mechanics change, it is a new gameplay/Cartridge version, not
merely a skin.

7. METROPOLIS SCOPE RULE
Before adding anything, ask:
Does this materially improve the end-to-end Metropolis demo, fix a
security/correctness issue, or prevent an architectural dead end?
If no, defer it.
In particular, do not opportunistically add:
• permissionless creator launches
• AI game generation
• multiplayer platform infrastructure
• advanced DynamicFeeStrategy
• automated NFT floor buying
• broad multichain deployment
• $TA
• betting / wagering
• marketplace systems
• full cosmetics marketplace
• clan / sprint systems
• shared Skeleton-wide leaderboards
unless the founder explicitly changes scope.

8. CODEX WORKING RULE
Before starting a task, identify:
Label: Source of Truth / Implementation Note / Research Note
Layer: Product / Protocol / Implementation / Research
Owning source: exact document
Acceptance test: observable behavior proving completion
Out of scope: what must not be redesigned
For application/game work:
The game supplies gameplay.
Token Arcade supplies the arcade.
For protocol work:
Hook captures/accounting.
Economy Router allocates.
Strategies act.
Vault holds.
Trigger decides when it is game time.
RaidManager settles the tournament economy.
9. CHANGE CONTROL
When a major product or economic decision changes:
1. Update the owning Source of Truth first.
2. Increment its revision/version if appropriate.
3. Add a short changelog entry.
4. Update affected Implementation Notes.
5. Then update code.
Do not let architecture drift through isolated chat messages or agent-generated
files.
